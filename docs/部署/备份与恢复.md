## 一、为什么这件事排在最前面

`DailyEvaluation` 与 `Session` 是这套系统的**全部历史资产**：谁哪天达标、凭哪 6 局判的、
每一句对话的原话、主管每一次裁定。库没了，**重建不出来**——

- 演习分是 LLM 打的，重跑会得到第三个版本（既不是当初那个分，也不是所谓「正确的分」）；
- 准入结论一旦发出去，人当天就去接真实询盘了，撤不回来；
- 标尺校准、红线裁定、审计流水，全是人一条一条攒出来的。

**云数据库自带的时间点恢复不是备份**，那是事故缓冲，窗口很短，而且账号本身出问题时它一起没。

## 二、三条命令

```bash
npm run backup           # 备份。默认备 DATABASE_URL 指向的库
npm run backup:verify    # ★ 真恢复一遍 ★ 起干净容器 → 灌进去 → 逐表比对行数
npm run backup:verify -- drill-prod-20260101-0300.dump   # 指定某一份
```

**备份存放**：`<项目根目录的上一层>/_数据库备份/`（**在 git 仓库外面**）。
每份两个文件：

| 文件 | 是什么 |
|---|---|
| `drill-<来源>-<日期>-<时分>.dump` | pg_dump 的 custom 格式（自带压缩、可选择性恢复） |
| 同名 `.json` | 清单：时间、来源、服务端版本、文件大小、**sha256**、**逐表行数**、验证时间 |

那份 `.json` 不是装饰——**恢复验证就是拿它对账**，没有它，你只能知道「文件在」，
不知道「数据全不全」。

## 三、备线上库要先做一件事

`.env` 里的 `DATABASE_URL` 一般指向本地开发库，直接跑 `npm run backup` 备的是**本地开发库**。

要备线上库：

1. 从托管平台的环境变量或云数据库控制台复制出线上库的连接串；
2. 写进本仓 `.env` 的 **`BACKUP_DATABASE_URL`**；
3. `npm run backup && npm run backup:verify`。

> ### ★ 两条别踩的 ★
>
> **① 别改 `DATABASE_URL` 去备份。** 改了它，本地开发就直接连上线上库了——
> 一次 `prisma db push`、一次 seed，就能把线上数据改掉，而且不会有任何提示。
> 脚本专门认 `BACKUP_DATABASE_URL` 就是为了不让人动那一个。
>
> **② 要直连串，不要连接池串。** 像 Neon 那种带 `-pooler` 的端点后面是 pgbouncer（事务模式），
> 不支持 pg_dump 要的会话级特性。脚本会自动把 `-pooler` 去掉，但你自己复制时也注意——
> 这是「备份为什么一直失败」最常见的答案。

## 四、库没了怎么办（恢复流程）

### 4.1 先别急着恢复，先确认三件事

1. **是数据没了，还是连不上？** 连不上就是云数据库服务的事，去控制台看，别急着灌数据。
2. **最新那份备份是什么时候的？** 看 `_数据库备份/` 里最新的 `.json` 的 `at`。
   从那一刻到现在的数据是**找不回来的**——先想清楚这段时间发生过什么
   （有没有人考过试、主管改过谁的期别），恢复完要手工补。
3. **那份备份验过没有？** `.json` 里的 `verifiedAt` 不是 `null` 才算验过。

### 4.2 先在本地验一遍，再往线上灌

```bash
npm run backup:verify -- <那份文件名>
```

**永远先跑这一步。** 它会起一个独立容器把数据灌进去、逐表对行数，不碰任何线上东西。
这一步过不了，说明那份备份本身有问题，往线上灌只会把事情弄得更糟。

### 4.3 灌进一个新库

```bash
# 1. 在云数据库控制台建一个新数据库，拿到直连串
# 2. 建表结构
DATABASE_URL='<新库直连串>' npx prisma migrate deploy

# 3. 灌数据（--data-only：只灌数据，不动上一步建好的结构）
docker run --rm -i -e PGURL='<新库直连串>' postgres:17-alpine \
  sh -c 'pg_restore --data-only --no-owner --no-privileges -d "$PGURL"' \
  < "../_数据库备份/<那份文件>.dump"

# 4. 对行数：和那份 .json 里的 rows 逐个对
```

> **为什么第 3 步用 `--data-only`**：`migrate deploy` 已经把表建好了，
> 直接全量恢复会撞「已存在」的错误刷一屏，然后你分不清哪些是真错。
> 如果是往一个**完全空的**库里恢复，可以不加 `--data-only`，让 dump 自己建表。

### 4.4 切回去

把新库的连接串写回线上环境变量 `DATABASE_URL`（云数据库建议用连接池串，
只有备份和恢复用直连），重新部署。

## 五、多久备一次

现在是**手动**：`npm run backup`。

要自动，先把线上库连接串按第三节配好，再加一条每天 03:00 的定时任务。

Windows（任务计划）：

```powershell
schtasks /Create /TN "询盘系统-每日备份" /SC DAILY /ST 03:00 /TR ^
  "cmd /c cd /d \"<项目目录>\" && npm run backup"
```

> ★ 这台机器关机的时候不会跑 ★ 这是本方案最大的短板，写在这儿别自欺欺人。
> 真要「不依赖某台电脑」，得把备份挪到云上（GitHub Actions 定时跑 pg_dump），
> 但那意味着**把线上库的连接串交给 GitHub、把导出的数据放在 GitHub 上**——
> 那是一个要单独决定的事，不该顺手做掉。
>
> 折中做法：任务计划照上面加，**再把 `_数据库备份/` 目录挂进网盘同步**（坚果云/OneDrive 都行）。
> 这样「电脑坏了」也还有一份，而数据始终在自己手里。

**每月至少跑一次 `npm run backup:verify`。** 备份机制烂掉的方式从来不是「报错」，
是「一直在跑、一直没人验、需要的那天发现导出来的是空的」。

## 六、这套东西是怎么验过的

不是「写完就算」，当天真跑过：

| 步骤 | 结果 |
|---|---|
| 备份本地库 | `drill-local-<日期>-<时分>.dump`，约 0.35 MB，21 张表 |
| 校验和 | 一致 |
| **真恢复** | 起干净的 `postgres:16-alpine` → `pg_restore` → **21 张表逐一对上** |
| 清理 | 验证容器自动拆掉，不留残留 |

过程中撞到并修掉的三个坑，都写进脚本注释了，这里留个索引：

1. **`?schema=public` 是 Prisma 专有参数**，libpq 不认，pg_dump 直接报
   `invalid URI query parameter: "schema"`——那句话看不出是串的问题还是库的问题。
2. **容器里的 `localhost` 是容器自己**。把 `localhost:5433` 传进 pg_dump 容器，
   它连的是自己，报 `connection refused`，很容易被读成「数据库挂了」。
3. **`SHOW server_version` 的列名不是 `v`**，取不到会静默落成 `unknown` →
   镜像退回最低版本 16 → 真连上 PG 17 时被拒。一个静默默认值，
   换来的是备份在最需要它的那天才失败。

## 七、限制，写清楚

| 限制 | 说明 |
|---|---|
| **线上库要单独配** | 连接串默认不在本机，见第三节。**没配好之前，等于还没有备份。** |
| 依赖这台电脑 | 关机就不跑。见第五节的折中做法 |
| 依赖 Docker | 本机没有 `pg_dump`，全靠 docker 里的。Docker Desktop 没开就跑不了 |
| 备份是全量 | 本地库约 0.35 MB，线上库大一些但同量级。不做增量——这个体量不值当 |
| 不含密钥 | dump 里只有业务数据。`AUTH_SECRET` 之类在线上环境变量里，**那些要单独记在别处** |
